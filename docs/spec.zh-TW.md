# IR 膠囊中繼器（Record & Redirect）專案規格大綱

> 英文說明與接線圖見專案根目錄 `README.md` 與 `docs/wiring.html`；本文件為中文規格與設計討論紀錄。

> 給實作者（另一個 AI / 工程師）的交接文件。目標：以 ESP32-C3 實作韌體、Web BLE 設定網頁與硬體接線說明。
> 狀態標記：**[定案]** 已與需求方確認；**[建議]** 建議做法，可依實作調整；**[待確認]** 需要需求方回答。

## 1. 專案目標

用一支市售「通用遙控器」控制多台家電，且不干擾家電本身。

- 通用遙控器被設定成一組**所有家電都不會反應的「假代碼」**（假頻道）。
- 本裝置（透明扭蛋殼內）接收假代碼，依對照表**轉發成對應家電的真實紅外線訊號**。
- 同一支遙控器可用「圖層（layer）」切換，控制更多家電。
- 設定（錄製真遙控器、對照表、巨集）透過 **Web Bluetooth 網頁** 完成；C3 本身不提供網頁。
- NFC 貼紙貼在裝置上，感應後直接開啟設定／使用頁面。

### 為什麼用假頻道 **[定案]**
1. 家電不會對通用遙控器直接反應，避免「家電自己動 + 裝置又轉發一次」的重複觸發。
2. 裝置只接受假代碼表內的訊號；它自己發出的真代碼不在表內，因此**不會自我觸發迴圈**。

### 非目標
- 不做網頁伺服器（C3 不跑 HTTP server）。
- 不使用 TF 卡。
- RF（433MHz）控制不在此版範圍。

## 2. 系統架構

```
通用遙控器 (假代碼)
      │ IR
      ▼
[VS1838B ×1~4] ─► ESP32-C3 Super Mini ─► [ULN2003APG] ─► [IR333C-A 環形 ×8] ─► 家電 (真代碼)
                       │  ├─ 板載藍燈 GPIO8 (狀態/layer 指示)
                       │  ├─ LittleFS (設定儲存)
                       │  └─ BLE (NimBLE GATT)
                       ▼
            手機/電腦 Chrome (Web Bluetooth) ◄── NFC 貼紙 (NDEF URL)
```

### 3.2 發射電路（ULN2003 驅動環形 LED）**[建議]**

- 8 顆 IR LED 分成 **4 串，每串 2 顆串聯 + 22Ω**。
- 每串：`5V → 22Ω → LED → LED → ULN2003 OUTn`。
- 4 路 ULN2003 輸入（IN1–IN4）**並在同一個 GPIO**（ULN2003 內建約 2.7kΩ 輸入電阻，3.3V 可直接驅動，不需基極電阻、不需 S8050）。
- ULN2003 腳位（DIP-16）：IN1–IN7 = 腳 1–7，GND = 腳 8，COM = 腳 9（LED 負載可空接），OUT7–OUT1 = 腳 10–16。
- 電流估算：5V − ULN 約 1V 壓降 − 2×LED 約 2.8V ≈ 1.2V，除 22Ω ≈ 55mA／串，4 串約 220mA 峰值（38kHz 載波約 1/3 佔空比，平均更低）。
- ULN2003 GND 必須與 ESP32 GND 共地。
- **3.3V 供電時兩顆串聯不夠壓降，需改單顆**。本設計使用 5V。

### 3.3 接收電路 **[建議]**

- VS1838B：VCC 接 3.3V（規格約 2.7–3.5V，**不要接 5V**），GND，OUT → GPIO。
- 不同型號腳位順序可能不同，**實物到貨先對照規格圖**（常見為 OUT、GND、VCC）。
- 多顆接收頭輸出腳並聯（低電位有效），用於 360° 接收。**先用 1 顆驗證，再增加到 3–4 顆**。
- 接收頭與發射 LED 之間需**黑色隔板**，避免自家發射把接收頭打到飽和。

### 3.4 建議腳位（Super Mini，可調整）**[建議]**

| 功能 | GPIO | 備註 |
|---|---|---|
| IR 接收 | 4 | |
| IR 發射（接 ULN2003 IN1–IN4） | 5 | |
| 板載 LED | 8 | 板載藍燈；GPIO8、GPIO2、GPIO9 為 strapping 腳，**避免作為 IR 腳** |
| 其他可選 I2C/感測 | 20/21 或 0/1/3/7/10 | 之後擴充用 |

### 3.5 機構

- 透明扭蛋殼（約 Ø65–75mm）。940nm 紅外線多數透明塑膠可穿透，**染色殼不行，先用手機相機實測**。
- LED 環繞一圈（約每 45° 一顆），接收頭夾在其間，各自以黑色隔片分隔。
- 板載藍燈若在殼內不易看見，可在殼上對應位置開小孔或貼導光材料（選配）。

## 4. 韌體（ESP32-C3）

### 4.1 技術選型 **[建議]**

- 框架：Arduino-ESP32（PlatformIO），或 ESP-IDF。
- 函式庫：`NimBLE-Arduino`、`ArduinoJson`、`LittleFS`。
- IR 收發：
  - `IRremoteESP8266` 可用於**接收與協議解碼**，但它的發送是軟體 bit-bang 載波，**不使用 RMT**。
  - 該函式庫與 C3、Arduino-ESP32 3.x 的相容性**必須在 M1 先驗證**。
  - 發送層需自行以 ESP-IDF RMT（硬體載波）實作，只借用函式庫的協議編碼（產生 mark/space 序列）。
  - 若函式庫相容性不佳，改為 ESP-IDF RMT 收發加自寫解碼（NEC／Sony／Samsung 等常見協議簡單，其餘存 raw）。
- 分區表：選擇有足夠 LittleFS 空間（≥1MB）的 4MB 方案。第一版不做 OTA，以 USB 更新韌體。

### 4.2 模組

1. **IR 接收／解碼**：已知協議（NEC、Sony、Samsung…）存解碼值；未知協議存 raw mark/space 時間序列與載波頻率。
2. **IR 發送**：依協議或 raw 重送，**以 RMT 硬體產生載波**；載波預設 38kHz，可依按鈕**手動**設定（VS1838B 輸出已解調，無法量測載波頻率）。
3. **規則引擎**：`(layer, 假代碼) → 動作列表`。
4. **巨集執行器**：動作序列，含延遲（非阻塞）。
5. **Layer 管理**：目前 layer、切換規則、以閃爍次數表示 layer。
6. **BLE GATT 服務**：config 讀寫、即時觸發按鈕、學習模式、狀態通知。
7. **設定儲存**：LittleFS（JSON 或二進位），另可用 NVS 存小參數。
8. **LED 狀態機**（板載藍燈 GPIO8，單色，以閃爍節奏區分狀態）。
9. **時間與排程**（選配，見 4.6）。

### 4.3 核心行為規則

- **只接受假代碼表內的訊號**；其他一律忽略（含自己發出的真代碼）。
- **發送期間暫停接收**，發送結束後保留約 50–100ms 保護時間，避免接收頭被飽和／誤收。
- **長按（repeat）**：NEC 等協議的 repeat frame 需處理；支援「按住持續轉發」或「只轉發一次」兩種模式（每個對應可設定）。
- **去彈跳**：同一代碼在短時間內重複收到需去重，但須區分「長按」與「連按」：
  - NEC 長按是 repeat frame，依 `repeat_mode` 處理。
  - RC5／RC6 有 toggle bit，連按同一鍵的代碼不同，**不可**當作重複丟掉。
  - 去重時間窗與規則放在 `settings`，可調整。
- **多圖層（layers）**：通用遙控器若有多個裝置模式（TV/DVD/AUX…），每個模式選一組不同的假代碼，各自對應一個 layer。目前 layer 可由收到的假代碼集合自動判定，或由專用按鈕切換（**[待確認]** 採哪種）。
- **IR 發射時序**：C3 為單核，BLE 中斷會使軟體產生的 38kHz 載波抖動。**採用 RMT 硬體載波**（C3 RMT 有 2 個 TX、2 個 RX 通道：IR TX 用一個 TX 通道，IR RX 可用 RX 通道）；備案：發送期間限制 BLE 活動。
- **學習流程**（兩種模式，流程相同）：
  - **學習真代碼**：錄製家電原廠遙控器的按鍵，存為按鈕的 `actions`。
  - **學習假代碼**：錄製通用遙控器的按鍵，存為按鈕的 `fake`。
  - 流程：網頁選擇目標按鈕與模式 → 寫入「學習」命令 → C3 進入學習模式（LED 慢閃）→ 使用者按下對應遙控器 → C3 解碼／錄製 → 回傳預覽並由網頁確認儲存。
  - 長 frame（如冷氣）需加大接收緩衝並設定足夠的 frame 結束逾時（約 50ms 以上）。
- **延遲預算**：NEC 接收約 68ms，轉發真代碼約 70ms 以上，冷氣長 frame 可達 200ms 以上。因此端到端延遲以 **frame 結束後 ≤ 100ms 開始發送** 為目標，不要求總時間 100ms 內完成。

### 4.4 板載藍燈狀態（**[建議]**，單色 GPIO8，注意多數 Super Mini 為低電位點亮）

| 狀態 | 表現 |
|---|---|
| 切換 layer | 閃 N 下（N = layer 編號 + 1） |
| 學習模式 | 慢閃（約 1Hz） |
| 轉發中 | 短閃一下 |
| BLE 已連線 | 恆亮 |
| 錯誤 | 快閃（約 5Hz）持續 2 秒 |
| 閒置（未連線） | 熄滅或極慢呼吸（可設定） |

- layer 的 `color` 欄位只用於網頁介面顯示，裝置本身不使用。

### 4.5 資料模型與儲存

#### 邏輯模型：訊號、裝置、對照分離（範例，格式可調整）

訊號只存一份，巨集以 `signal_id` 引用，避免重複。

```json
{
  "version": 2,
  "device_name": "IRCapsule-A1B2",
  "devices": [
    { "id": 1, "name": "客廳電視", "brand": "Sony", "type": "tv" },
    { "id": 2, "name": "客廳冷氣", "brand": "Daikin", "type": "ac" }
  ],
  "signals": [
    { "id": 10, "name": "通用遙控 TV-電源", "kind": "fake", "protocol": "NEC", "bits": 32, "value": "0x1234ABCD" },
    { "id": 20, "name": "電視 電源", "kind": "real", "device_id": 1, "protocol": "SONY", "bits": 12, "value": "0xA90" },
    { "id": 21, "name": "冷氣 開 26度", "kind": "real", "device_id": 2, "protocol": "RAW", "carrier_khz": 38, "blob": "<raw 序列，二進位存放>" }
  ],
  "layers": [
    {
      "id": 0,
      "name": "客廳",
      "color": "#00AAFF",
      "map": [
        { "fake": 10, "repeat_mode": "once",
          "macro": [ { "signal": 20 }, { "delay_ms": 2000 }, { "signal": 21 } ] }
      ]
    }
  ],
  "schedules": [],
  "settings": { "led_brightness": 40, "rx_guard_ms": 80 }
}
```

- **來源**：`kind = fake`，屬於某 layer 的觸發訊號（通用遙控器按鍵）。
- **對象**：`kind = real`，以 `device_id` 指向家電。
- **名稱**：`devices`、`signals`、`layers` 的名稱都存在裝置上，換手機連線也看得到。
- 網頁（static web）負責介面、編輯與備份；資料與轉發邏輯都在裝置上，斷線後仍可運作。

#### 儲存與容量

- 晶片為 ESP32-C3FH4（內建 4MB flash）；不做 OTA 時，LittleFS 可用約 1.5–2MB。
- 單筆訊號大小（二進位）：已知協議約 10–30B；家電 raw 約 150–400B；冷氣 raw 約 0.5–1.2KB；metadata 約 50–150B。
- 估算：100 個按鈕（多為已知協議）加 20 個冷氣 raw 約 50–100KB，1,000 個以上才接近 1MB。**容量不是限制，RAM 才是。**
- **不將整份 config 載入 RAM**（可用 heap 約 300KB，還要分給 BLE）：
  - RAM 只放索引（id、名稱、指標）。
  - 訊號本體在轉發時才從 flash 讀取。
- **訊號以二進位打包成單一檔案加索引**，不要每筆一個檔案（LittleFS 小檔案各佔 4KB 區塊，約 500 個檔就滿）。raw 資料不用 JSON 文字存放（體積約 3 倍）。
- 與網頁之間的 JSON 只用於匯出匯入與傳輸；裝置內部為二進位格式。
- BLE 傳輸約 5–20KB/s，網頁**以單一按鈕或單一 layer 為單位同步**，不整份讀寫。
- 寫入 flash 僅在設定變更時進行，無需擔心壽命。

#### 錄製與代碼庫

- **假代碼一定要錄**：通用遙控器的代碼由其品牌代碼庫決定，只能實際按鍵錄下。
- **真代碼可錄、可由代碼庫匯入**：
  - 常見協議可由「協議加位址加指令」直接產生。
  - 冷氣為狀態型協議，可由函式庫依品牌產生，錄製最保險。
  - 冷門或舊型號只能錄。
- **選配**：static web 一併託管公開 IR 代碼庫（如 Flipper-IRDB 資料），使用者選品牌與型號後，由網頁推送到裝置。

### 4.6 時間與排程（選配）

- C3 無 RTC：網頁連線時寫入手機時間（epoch），可支援「凌晨 2 點關冷氣」。
- **斷電後時間會遺失，需等下次連線才能校時**。本版僅使用 BLE，不使用 WiFi，也不加 RTC；排程只在手機曾連線校時後有效。

## 5. BLE 與 Web 設定網頁

### 5.1 BLE 設計要點 **[建議]**

- 廣播名稱含 MAC 後段（如 `IRCapsule-A1B2`），並廣播自訂 Service UUID 供網頁過濾。
- GATT 特徵值（建議最少集合）：
  - **Config 讀／寫**（分段傳輸：協商較大 MTU 後分塊，需有序號與結束標記／校驗）。
  - **Command 寫入**：觸發按鈕、進入學習、切換 layer、同步時間、恢復出廠。
  - **Status 通知**：目前 layer、學習結果、錯誤碼。
- **安全性 [定案：不做]**：不配對、不綁定、不加 PIN，任何人在 BLE 範圍內都能連線並讀寫設定。此為已接受的風險；若日後需要，可再加 BOOT 鍵（GPIO9）開啟限時寫入視窗。
- 同一時間只允許 1 個連線，避免多人同時寫入造成 config 損毀。

### 5.2 Web 網頁 **[定案：Web BLE 為載體，C3 不提供網頁]**

- 網頁**託管在外部**（如 GitHub Pages），必須 **HTTPS**。
- 瀏覽器限制：
  - Chrome（Android／桌面）支援 Web Bluetooth。
  - **iOS Safari 不支援**，iPhone 需使用 Bluefy 等支援的瀏覽器。
  - `requestDevice()` 必須由**使用者點擊**觸發，因此 NFC 開啟網頁後仍需點一次「連線」。
- 網頁做成 **PWA**（service worker 快取），家中沒有外網時仍可開啟；Web Bluetooth 本身不需要網路。
- 功能：
  - 連線、讀取 config，**由 config 動態產生按鈕介面**。
  - 學習／錄製按鈕、編輯對照表與巨集、設定 layer 名稱與顏色。
  - 即時觸發（BLE 主動操控）。
  - **匯出／匯入 JSON 備份**。
  - 時間同步、（選配）韌體資訊。

### 5.3 NFC **[建議]**

- NTAG 貼紙寫入 NDEF URL，例如 `https://<host>/app/?device=IRCapsule-A1B2`。
- 網頁依 `device` 參數提示使用者連線到對應裝置；仍需使用者點擊按鈕觸發連線。
- 限制：
  - `device` 參數**無法預選裝置**，瀏覽器仍會跳出裝置選擇視窗，網頁只能用名稱前綴過濾並提示。
  - Android 感應 NFC 時可能用非 Chrome 的預設瀏覽器開啟，而 Web Bluetooth 需要 Chrome 系。需在文件註明，並建議將 Chrome 設為預設瀏覽器，或在頁面偵測不支援時提示用 Chrome 開啟。

## 6. 可選擴充（後續，不在第一版）

- 感測器：I2C 溫濕度（AHT20）、光感，達條件自動發送指令。
- 霍爾開關（US1881）門磁：開門觸發 IR 動作。
- EL817 光耦：隔離偵測門鈴／設備狀態。
- SRD-05VDC 繼電器（由 ULN2003 驅動）：遙控插座（市電需注意安全）。
- WiFi + MQTT / Home Assistant 橋接。
- WiFi OTA 韌體更新。

## 7. 風險與注意事項

| 風險 | 緩解 |
|---|---|
| 假代碼誤觸家裡的電器（**最大未知數**） | 通用遙控器的代碼庫是預設的，無法自訂；需逐模式用實體遙控器測試，找出家裡所有家電都不反應的代碼組，且每個 layer 都要各找一組。列入 M1 驗證 |
| 學習時無法得知載波頻率 | VS1838B 輸出已解調；預設 38kHz，非 38kHz 家電由使用者手動設定 |

| 殼內自我干擾（接收頭被自己飽和） | 隔板 + 發送期間暫停接收 + 保護時間 |
| 載波被 BLE 中斷抖動 | RMT 硬體載波；備案限制發送時 BLE 活動 |

| 射程／視線 | 環形發射；先確認每台電器位置 |
| VS1838B 腳位因型號而異 | 到貨後對照規格圖再接線 |
| 接收頭多顆並聯串擾 | 先 1 顆驗證，再增加 |
| 鄰近者修改設定 | 已接受（不做安全機制）；僅允許單一連線，並保留匯出備份供還原 |

## 8. 里程碑與驗收

1. **M1 基礎 IR 與關鍵風險驗證**：
   - 接收並印出解碼結果；發送一個已知代碼能控制實體家電。
   - 驗證 IR 函式庫在 C3 上可用（含接收長 frame），並以 RMT 完成硬體載波發送。
   - 用實體通用遙控器找出「家電無反應」的假代碼組，確認每個欲用的模式都有可用代碼。
   - 在實際殼內（或模擬隔板）測試：發射時接收頭是否被打飽和，保護時間是否足夠。
2. **M2 發射環**：ULN2003 + 4 串 LED，量測電流並確認射程與覆蓋角度。
3. **M3 轉發核心**：假代碼 → 真代碼對照（硬編碼測試），含 repeat 與 guard 時間。
4. **M4 設定儲存**：LittleFS 讀寫 config，重開機後保留。
5. **M5 BLE + 網頁**：連線、讀寫 config、觸發按鈕、學習流程、匯出／匯入。
6. **M6 圖層與 LED**：多 layer 切換與板載藍燈狀態。
7. **M7 機構整合**：裝入扭蛋、隔板、NFC、整體實測。

**驗收範例**
- 通用遙控器按任一假按鈕，裝置在收完 frame 後 100ms 內開始發送，對應家電收到正確指令，且家電不會被通用遙控器直接觸發。
- 發射時裝置不會因為自身訊號而重複觸發。
- 斷電重開後，所有按鈕對照與 layer 保持。
- 手機 Chrome 感應 NFC 後，點一次連線即可看到並操作所有按鈕。
