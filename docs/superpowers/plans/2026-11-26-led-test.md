# LED Test Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Blink all IR LEDs from BLE, USB or the web page to check the soldering with a phone camera.

**Architecture:** A `ledtest` command starts one job on the existing executor task, which loops
DC pulses through `ir_send_raw` until switched off or timed out. The web page adds one button.

**Tech Stack:** ESP-IDF v6.1 (C), single-file web page `web/index.html`.

**Spec:** `docs/superpowers/specs/2026-11-26-led-test-design.md`

## Global Constraints

- 0.5 s on, 0.5 s off, no carrier, stops by itself after 60 s.
- Command `ledtest`, argument `on` (0/1, default 1).
- Docs, code and tool output in English; web strings in English and zh-TW. No device paths or MACs in files.
- Flash only our board, through `IRCAP_PORT` set to its by-id path.
- The folder is not a git repository: no commit steps.

## Review Focus

- `ledtest` on twice: one blink job only; the second call restarts the 60 s.
- `ledtest` off during a test: dark within 0.5 s, and a following `fire` is sent.
- `ledtest` off when idle: replies ok, nothing lights.
- Client disconnects mid-test: LEDs still stop at 60 s.
- Reception after the test: `inject` and real frames behave as before.

### Task 1: Firmware command

**Files:**
- Create: `firmware/tools/ledtest_check.py`
- Modify: `firmware/main/engine.c`, `firmware/main/engine.h`, `firmware/main/proto.c`, `docs/protocol.md`

**Interfaces:**
- Produces: `bool engine_ledtest(bool on);` (false only if the job queue is full); protocol
  `{"cmd":"ledtest","on":1}` -> `{"ok":true}` or `{"ok":false,"err":"busy"}`; log lines
  `led test on` and `led test off`.

- [ ] **Step 1: Write the failing test** `ledtest_check.py` (uses `Capsule` from `ircclient`, non-destructive, same `check()` style as `selftest.py`). Checks:
  - `ledtest on=0` while idle is ok.
  - `ledtest on=1` twice: both ok; exactly one `led test on` log.
  - after 3 s, `ping` and `info` still answer.
  - `play khz=38 raw=[560,560,560]` during the test: no `sent raw` log within 1 s.
  - `ledtest on=0`: within 1.5 s the logs show `led test off`, then `sent raw ... ok`.
  - `ledtest on=1`, then wait up to 63 s: `led test off` arrives between 59 s and 62 s after the start.
- [ ] **Step 2: Run** `python3 firmware/tools/ledtest_check.py` on the current firmware (IDF venv Python). Expected: FAIL (`unknown cmd`).
- [ ] **Step 3: Implement** `engine_ledtest` and `JOB_LEDTEST` in the engine, the command in `proto.c`, and one row in `docs/protocol.md`.
  Keep a `volatile int64_t` deadline and a "job queued or running" flag. One pulse is
  `ir_send_raw` with `carrier_khz = 0` and ten pairs `{50000, 0}`: zero-length spaces are
  skipped, so the marks join into 500 ms. This also sets the self-reception guard.
  Delay 500 ms after each pulse.
- [ ] **Step 4: Build, flash, run** `ledtest_check.py`. Expected: ALL PASS.
